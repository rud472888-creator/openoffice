# iPad portability: upstream PR review

Reviewed on 2026-11-05 against local baseline and upstream `pblsketch/openoffice/main` at `8a2dafdd9a7cb28d5f2635f007676841dadeaf08`.

The useful upstream improvements below are already in this checkout. Each implementation commit listed below was verified with `git merge-base --is-ancestor <commit> HEAD`. There is no new upstream patch to cherry-pick from this shortlist. A separate browser host can reuse the applicable behavior without changing document engines.

## Sources and scope

- Read the public GitHub PR descriptions and search results, and fetched the selected public PR refs into a separate temporary bare repository. Inspected the implementation diffs, rather than relying on the PR head commit: several heads contain only documentation or merge changes.
- `git ls-remote` verified the upstream main SHA and public PR refs through #325. GitHub's `is:pr ipad` search returned zero open and zero closed results. Searches for browser, web, touch, wasm, offline and responsive provided the candidates below; those words often referred to desktop behavior rather than mobile support.
- The seven selected PRs all report a merged state in GitHub's PR listing. This is a targeted portability review, not an exhaustive review of every upstream PR.
- GitHub `.patch` downloads redirected to a destination denied by the environment's HTTP policy. The same changes were inspected through the allowed Git transport instead. No upstream source changes, remote pushes or engine edits were made for this review.

The existing renderer-only Vite configurations are development servers for Electron-hosted renderers. They do not install browser substitutes for preload APIs:

- [`apps/docs/src/renderer/App.tsx`](../apps/docs/src/renderer/App.tsx) calls `window.desktop` for file, settings, recovery and AI services. [`file-actions.ts`](../apps/docs/src/renderer/file-actions.ts) already contains the DOCX parse/edit/save orchestration, while browser-neutral editor components can be reused individually.
- [`apps/markdown/src/renderer/main.tsx`](../apps/markdown/src/renderer/main.tsx) requires `window.markdownApi` during bootstrap.
- [`apps/slides/src/renderer/App.tsx`](../apps/slides/src/renderer/App.tsx) obtains its deck and edit operations from `window.slidesApi`.
- [`apps/sheets/src/renderer/App.tsx`](../apps/sheets/src/renderer/App.tsx) uses an Electron bridge and native sidecar session lifecycle alongside Univer. A browser spreadsheet UI alone does not replace the existing workbook read/save contract.

## Recommended application to the iPad work

1. Use an explicit browser host and browser capability boundary. Reuse the DOCX engine and editor components first; avoid mounting a desktop `App` with placeholder success responses for missing services.
2. Carry forward the reviewed small-screen patterns: directly collapsible panes, persisted view choices with storage-failure handling, typing-aware shortcuts, local assets, deferred optional features and bounded preview work.
3. Keep desktop CLI subscription providers unavailable in the browser. A browser cannot spawn the installed Claude or Codex programs. Do not silently switch to another billing route.
4. Keep document-engine behavior and identifiers unchanged. Any future browser PPTX/XLSX adapter needs its own verified open/edit/save path before the UI offers editable Office-file support.
5. Validate the browser host separately on Safari/iPadOS: composition and Korean input, selection handles, on-screen keyboard resizing, hardware shortcuts, touch scrolling, file import/export and interrupted-session recovery. None of the reviewed PRs supplies that acceptance evidence.

This review establishes source provenance and concrete reuse boundaries. It does not claim an upstream iPad implementation, iPad device testing, or new engine compatibility work.
